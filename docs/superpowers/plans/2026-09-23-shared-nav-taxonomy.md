# Shared Navigation Taxonomy Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Render the shared navigation taxonomy on both clients, and close the four divergences grouping alone cannot fix — web's missing Review Categories screen, Ask Fyn's two interaction models, the unshared notification surface, and the orphaned `/app/wrapped` route.

**Architecture:** Groups and membership are shared; rendering is platform-native — the rule Settings already follows, extended from the Settings level to the top level. Web's sidebar gains section headers; mobile's More menu gains the same sections and a shared header-actions component generalised from the search button already in the Dashboard greeting row. The tab bar stays a shortcut layer, with promoted items still listed in their groups.

**Tech Stack:** React + TypeScript + Vite + Vitest (web), React Native + Expo + Jest (mobile), React Navigation, TanStack Query, Micrometer-backed nav counters from the companion plan.

**Spec:** [docs/superpowers/specs/2026-09-23-shared-nav-taxonomy-design.md](../specs/2026-09-23-shared-nav-taxonomy-design.md)

## Global Constraints

- **Promotion never changes taxonomy membership.** Transactions and Insights are tabs *and* group entries; Import Statement is the FAB *and* a group entry. Removing a promoted item from its group is a taxonomy violation, not a cleanup.
- **Groups are static sections, not accordions.** Nothing expands or collapses per group. The only collapse is the existing whole-sidebar `w-64`/`w-20` toggle.
- **Group headers are never selectable** — no route, no focus, no active state.
- **Membership is shared; containers are platform-native.** Web keeps "Your Account" in the avatar popup; mobile renders it as a More section. Both hold the same five items.
- Labels: `Dashboard` → **Home**; `Billing` → **Subscription**. The route `/app/billing` is **not** renamed — labels change, routes do not.
- The three review result sets are **disjoint by server design** and must render together on one screen. Rendering them as alternative tabs silently hides part of the backlog.
- Repo rule: commit messages carry no `Co-Authored-By` or AI-attribution trailer (project `CLAUDE.md`).

Home renders ungrouped at the top. Then each group renders an `<h3>` followed by its items. Collapsed, the `<h3>` is replaced by an `<hr>` separator — group headers have no legible text rendering at 80px.

```tsx
<nav className="flex-1 space-y-1">
  {renderItem(NAV_TAXONOMY.find((e) => e.group === 'root')!)}

  {NAV_GROUP_ORDER.map((group) => (
    <div key={group} className="pt-3">
      {collapsed
        ? <hr className="border-white/10 mx-2 mb-2" />
        : <h3 className="px-3 pb-1 text-[10px] font-semibold uppercase tracking-wider text-fixed-ink-3">
            {GROUP_LABEL[group]}
          </h3>}
      {/* Filtered by ROUTE, not just by group: a taxonomy member with no web route (ask-fyn) is
          rendered by its own affordance elsewhere and must not appear here as a dead link. */}

  ))}

```

import { Pressable, StyleSheet, View } from 'react-native';
import Ionicons from '@expo/vector-icons/Ionicons';
import { useNavigation } from '@react-navigation/native';
import { trackNavigation, trackNavSearch } from '../lib/trackNavigation';
import { spacing, useTheme } from '../theme';

/**
 * The persistent action row for primary tab destinations.
 *
 * Generalised from the search button that already lived in DashboardScreen's greeting row -- that
 * row was mobile's de facto TopBar, limited to one screen and one action.
 *
 * Hosted only on primary tab destinations, because those are the app's persistent work surfaces.
 * Secondary and pushed screens keep their existing patterns, where a native back affordance takes
 * priority over a row of global actions. More is a menu rather than a work surface; Import is a
 * FAB-triggered flow rather than a tab destination.
 *
 * Theme and Help are deliberately absent. Theme is a set-once preference already in
 * Settings -> General on both clients, and Support now sits in the More menu's Your Account group,
 * which is shorter than a header menu would be.
 */
export function ScreenHeaderActions() {
  const c = useTheme();
  const navigation = useNavigation<any>();

  return (
    <View style={styles.row}>
      <Pressable
        onPress={() => { trackNavSearch(); navigation.navigate('Transactions'); }}
        hitSlop={10}
        accessibilityRole="button"
        accessibilityLabel="Search transactions"
      >
        <Ionicons name="search-outline" size={22} color={c.muted} />
      </Pressable>

      <Pressable
        onPress={() => { trackNavigation('ask-fyn', 'header'); navigation.navigate('More', { screen: 'Fyn' }); }}
        hitSlop={10}
        accessibilityRole="button"
        accessibilityLabel="Ask Fyn"
      >
        <Ionicons name="sparkles-outline" size={22} color={c.muted} />
      </Pressable>

      {/* Bell behaviour arrives in Task 5; it renders here from the start so the row's layout is
          settled before unread state is added to it. */}
      <Pressable hitSlop={10} accessibilityRole="button" accessibilityLabel="Notifications">
        <Ionicons name="notifications-outline" size={22} color={c.muted} />
      </Pressable>
    </View>
  );
}

const styles = StyleSheet.create({
  row: { flexDirection: 'row', alignItems: 'center', gap: spacing.md },
});
```

### Task 4: Mobile notification read-state

**Files:**
- Create: `mobile/src/lib/notificationReadState.ts`
- Create: `mobile/src/lib/notificationReadState.test.ts`

**Interfaces:**
- Consumes: `mobile/src/lib/safeStorage.ts`.
- Produces: `useNotificationReadState(email: string | null, notifications: string[]) -> { unreadCount: number; loaded: boolean; markAllRead: () => void }`. Task 5 consumes it.

**The trap this task exists to avoid.** Web's `safeStorage` wraps `localStorage` and is synchronous, so `TopBar.tsx` derives the read set during state initialisation. Mobile's wraps `expo-secure-store` and is **Promise-based**. A straight port therefore renders every notification as unread until the stored set resolves — a bug the synchronous web implementation structurally cannot have, which is why porting web's code would sail through review.

 * Read-state is device-local and does not synchronise -- already true of web today, so not a
 * regression, but worth stating: web's is scoped to one browser profile, mobile's to one app
 * install. Reading a notification on one device never marks it read on another. Making it
 * server-side would be a backend change and is out of scope.
 */
const key = (email: string | null) => `finora_read_notifications_${email ?? 'anonymous'}`;

export function useNotificationReadState(email: string | null, notifications: string[]) {
  const [readIds, setReadIds] = useState<Set<string>>(new Set());
  // `loaded` exists because SecureStore is async where web's localStorage is not. Without it the
  // first render would show every notification as unread and then correct itself -- a flash the
  // synchronous web implementation cannot produce, and the reason this hook is not a direct port.
  const [loaded, setLoaded] = useState(false);

  useEffect(() => {
    let cancelled = false;
    void (async () => {
      const raw = await safeStorage.getItem(key(email));
      if (cancelled) return;
      try {
        setReadIds(new Set(raw ? (JSON.parse(raw) as string[]) : []));
      } catch {
        setReadIds(new Set());  // unreadable storage means nothing is known-read, not a crash
      }
      setLoaded(true);
    })();
    return () => { cancelled = true; };
  }, [email]);

  const markAllRead = useCallback(() => {
    const next = new Set(notifications);
    setReadIds(next);
    void safeStorage.setItem(key(email), JSON.stringify([...next]));
  }, [email, notifications]);

  return {
    loaded,
    unreadCount: loaded ? notifications.filter((n) => !readIds.has(n)).length : 0,
    markAllRead,
  };
}
```

- [ ] **Step 3: Build the screen**

```tsx
import { useQuery, useQueryClient } from '@tanstack/react-query';
import { transactionsApi, categoriesApi } from '../api/endpoints';

/**
 * The categorization correction loop on web — the counterpart to mobile's CategoryReviewScreen.
 *
 * The three queries below PARTITION the review backlog; they are not three views of one list.
 * The server removes anything returned by the group queries from the singles list, and a
 * merchant-matched row never reaches the counterparty grouping (TransactionService.java:882-885,
 * TransactionGroupingService.java:21-23). So all three render together, always. Presenting them as
 * tabs or as a filter would silently hide part of a user's backlog — the one failure mode this
 * screen is arranged to avoid.
 */
export function ReviewCategories() {
  const queryClient = useQueryClient();

  const singlesQ = useQuery({
    queryKey: ['transactions', 'needs-review'],
    queryFn: () => transactionsApi.needsReview(),
  });
  const groupsQ = useQuery({
    queryKey: ['transactions', 'needs-review', 'groups'],
    queryFn: () => transactionsApi.needsReviewGroups(),
  });
  const counterpartyQ = useQuery({
    queryKey: ['transactions', 'needs-review', 'counterparty'],
    queryFn: () => transactionsApi.needsReviewByCounterparty(),
  });
  const categoriesQ = useQuery({ queryKey: ['categories'], queryFn: () => categoriesApi.list() });

  // Any correction can move a row between partitions, so all three are invalidated together.
  const refetchAll = () => Promise.all([
    queryClient.invalidateQueries({ queryKey: ['transactions', 'needs-review'] }),
  ]);

  async function applySingle(id: string, category: string) {
    await transactionsApi.updateCategory(id, category);
    await refetchAll();
  }

  async function applyGroup(transactionIds: string[], category: string) {
    await transactionsApi.bulkRecategorize(transactionIds, category);
    await refetchAll();
  }

  const loading = singlesQ.isLoading || groupsQ.isLoading || counterpartyQ.isLoading;
  const total = (singlesQ.data?.length ?? 0) + (groupsQ.data?.length ?? 0)
    + (counterpartyQ.data?.length ?? 0);

  return (
    <div className="space-y-8">
      <h1 className="text-2xl font-bold text-ink font-display">Review categories</h1>

      {/* Empty state keys off the TOTAL across all three, never off one being empty. */}
      {!loading && total === 0 && <EmptyState title="Nothing to review right now" />}

      <section>
        <h2 className="font-semibold text-ink">By merchant</h2>
        {groupsQ.data?.map((g) => (
          <GroupRow key={g.merchant} label={g.merchant} count={g.transactionIds.length}
                    categories={categoriesQ.data ?? []}
                    onApply={(category) => applyGroup(g.transactionIds, category)} />
        ))}
      </section>

      <section>
        <h2 className="font-semibold text-ink">By counterparty</h2>
        {counterpartyQ.data?.map((g) => (
          <GroupRow key={g.counterparty} label={g.counterparty} count={g.transactionIds.length}
                    categories={categoriesQ.data ?? []}
                    onApply={(category) => applyGroup(g.transactionIds, category)} />
        ))}
      </section>

      <section>
        <h2 className="font-semibold text-ink">Individual transactions</h2>
        {singlesQ.data?.map((t) => (
          <SingleRow key={t.id} transaction={t} categories={categoriesQ.data ?? []}
                     onApply={(category) => applySingle(t.id, category)} />
        ))}
      </section>
    </div>
  );
}
```

`GroupRow` and `SingleRow` are local presentational components: a label, a count, a category `<select>` built from `categories`, and a confirm button calling `onApply`. Reuse the existing `CategoryCombobox` (`frontend/src/components/CategoryCombobox.tsx`) for the picker rather than writing a new one.
